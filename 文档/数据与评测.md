# 数据与评测(AOI 前端 × Azukiiro 评测后端)

> 本文档基于对 `aoi`(main 分支)与 `azukiiro`(main 分支)两个仓库的完整分析,聚焦**评测相关的数据结构**与**前后端协作方式**。
>
> 核心结论:**AOI 服务端不做任何评测计算**。它只负责数据存储(OSS)+ 任务分发(MongoDB 状态机),评测执行与排行榜计算全部由注册在组织下的外部评测机 **runner**(azukiiro)完成。因此"数据"分为两套体系:
>
> 1. **AOI 侧数据模型**(题目数据包、提交 Solution、评测详情、排行榜 JSON)——由前端直接消费;
> 2. **Azukiiro 侧评测模型**(ProblemConfig、SolutionInfo、SolutionDetails、适配器)——由评测机消费与产出。
>
> 两者通过 Runner 任务分发协议(REST + 预签名 URL)衔接。相关仓库:
> - 前端/服务端:https://github.com/fedstack-org/aoi
> - 评测机:https://github.com/fedstackjs/azukiiro

## 一、总体架构与数据流

```
┌────────────────┐      HTTP /api       ┌─────────────────────────────────────────────┐
│  前端 (Vue 3)   │ ───────────────────▶ │              AOI Server                    │
│  ProblemSubmit │   提交/查询/榜单      │  Fastify + MongoDB + OSS(S3 兼容)           │
│  SolutionView  │ ◀─────────────────── │  仅存储与调度,不评测                         │
└────────────────┘   problem-config.json │  - problems.data[] / currentDataHash        │
                                        │  - solutions(SolutionState 状态机)           │
                                        │  - runners(评测机注册/鉴权)                   │
                                        │  - contests.ranklistState(VALID/INVALID)     │
                                        └───────────────┬─────────────────────────────┘
                                                        │ Runner 任务分发协议
                                                        │ (X-AOI-Runner-Id / X-AOI-Runner-Key 鉴权)
                          ┌─────────────────────────────┼──────────────────────────────┐
                          ▼                             ▼                              ▼
              ┌─────────────────────┐   ┌──────────────────────┐   ┌──────────────────────┐
              │  azukiiro daemon    │   │  azukiiro ranker     │   │  azukiiro instancer  │
              │  评测守护进程        │   │  排行榜计算器         │   │  沙箱实例(环境)       │
              │  judge 适配器体系    │   │  (需 MongoDB)        │   │  docker 适配器        │
              │  uoj/deno/glue/...  │   │                      │   │  (compose 隔离环境)   │
              └─────────┬───────────┘   └──────────────────────┘   └──────────────────────┘
                        ▼
              ┌───────────────────────────────┐
              │  本地存储 storagePath/        │
              │  cache/<sha256>  数据缓存     │
              │  tmp/            解压临时目录  │
              │  instances/      实例目录      │
              └───────────────────────────────┘
```

**端到端数据流(提交一道题到榜单刷新)**:

```
1. 用户前端提交  →  POST /api/problem/:id/solution {hash,size}
                 →  state=CREATED(0),解答 zip 经预签名 URL 上传 OSS(solution/{id}/data)
2. 用户前端 submit →  POST /api/problem/:id/solution/:sid/submit
                 →  state=PENDING(1)
3. azukiiro daemon 轮询  →  POST /api/runner/solution/poll
                 →  服务端 findOneAndUpdate 抢占该任务:state=QUEUED(2),绑定 runnerId/taskId
                 →  返回完整 problemConfig + 题目数据/解答数据下载 URL(含 sha256)
4. azukiiro 评测  →  下载并校验两份数据(cache/<hash> 缓存)
                 →  PATCH 上报 {status:"Running", score:0, message:"Judging"}
                 →  按 problemConfig.judge.adapter 调用对应适配器评测
5. azukiiro 完成  →  评测详情 JSON 经预签名 URL 上传 OSS(solution/{id}/result.json)
                 →  POST .../complete → state=COMPLETED(4)
                 →  服务端同步 contestParticipants.results[problemId].lastSolution
                 →  比赛 ranklistState 置 INVALID
6. azukiiro ranker 轮询  →  增量同步 participants/solutions
                 →  按规则生成排行榜 JSON → 上传 OSS(contest/{id}/ranklist/{key}.json)
                 →  POST .../complete → ranklistState 置 VALID
7. 前端刷新榜单  →  GET /api/contest/:id/ranklist/:key/url → 渲染
```

## 二、评测数据模型(AOI 侧)

### 2.1 题目数据包(problem.zip)与 problem-config

题目的**测试数据、checker、spj 脚本、评测配置全部打包在一个 zip 里**,随"数据版本"上传:

- 前端 `DataUpload.vue` 上传 zip 时,自动从 zip 中提取 `problem.json`(兼容 `problem.yaml`/`problem.yml`),用 Monaco 编辑器在**线编辑并做实时 schema 校验**(`apps/frontend/src/components/problem/DataUpload.vue`,注册于 `fileMatch: ['problem.json']`);
- 服务端按版本管理:`problems.data[]`(每项 `{hash, config, description, createdAt}`)+ `currentDataHash` 指向当前生效版本,OSS key 为 `problem/{problemId}/data/{hash}`(`apps/server/src/oss/key.ts`);
- zip 内部结构**不强制约定**——除 `problem.json` 外的一切(测试数据、checker 等)由评测机端 `judge.adapter` 解释。

**problem.json 的完整 schema**(`aoi/libs/common/src/schemas/problem.ts`,公开为 `GET /schemas/problem-config.json`):

| 字段 | 类型 | 说明 |
|---|---|---|
| `label` | string | 题目名称(前端提交页标题) |
| `solution.maxSize` | integer | 提交文件体积上限(字节),默认 10 MiB |
| `judge.adapter` | string | **必填**。评测适配器名,由 runner 识别(azukiiro: `uoj` / `deno` / `glue` / `dummy` / `flag` / `vjudge`) |
| `judge.config` | object | **必填**。评测配置自由对象,由 adapter 端解释(测试点、checker、extraFiles 等都在这里),AOI 不约束 |
| `submit` | object | 提交方式:`upload`(文件)/ `zipFolder`(目录打包)/ `form`(表单多文件,`FormEditor` 逐文件编辑,提交时前端 jszip 打包) |
| `instanceLabel` / `instance` | string / object | 沙箱实例关联:`instance.adapter` + `instance.config` |
| `variables` | map | 任意变量(前端题面渲染用) |

**可见性差异(安全关键)**:
- 普通用户 GET `/api/problem/:problemId` 返回的 config **剔除 `judge` / `instance`**(`apps/server/src/routes/problem/scoped.ts:65`,比赛内题目同样 omit),避免泄露测试数据配置;
- 只有 runner 在 poll 响应中拿到**完整** `problem-config`(`apps/server/src/routes/runner/solution.ts`)。

### 2.2 提交(Solution)

服务端 `solutions` 集合(`apps/server/src/db/solution.ts`):

**`state`——整数状态机(服务端与前端共同理解)**:

| 值 | 常量 | 含义 |
|---|---|---|
| 0 | CREATED | 已创建(拿到上传 URL),尚未提交评测 |
| 1 | PENDING | 已提交,等待评测机认领 |
| 2 | QUEUED | 已被评测机认领(taskId 已绑定),排队中 |
| 3 | RUNNING | 评测中 |
| 4 | COMPLETED | 评测完成 |

**字段**:`_id, orgId, problemId, contestId?, userId, label, problemDataHash, state, solutionDataHash, score, metrics(Record<string,number>), status(string), message, runnerId?, taskId?, createdAt, submittedAt?, completedAt?, preferPrivate?`

**`status`——judger 产出的字符串**(前端只做展示映射,`apps/frontend/src/components/solution/SolutionStatus.ts`):

| 映射 | 说明 |
|---|---|
| `Accepted` / `Success` | AC |
| `Wrong Answer` | WA |
| `Time Limit Exceeded` | TLE |
| `Memory Limit Exceeded` | MLE |
| `Compile Error` | CE |
| `Runtime Error` | RE |
| `Internal Error` | 评测机内部错误 |
| `Running` / `Queued` | 过程状态 |

### 2.3 评测详情(result.json,存 OSS)

schema(`aoi/libs/common/src/schemas/solution.ts` `SSolutionDetailsSchema`),OSS key `solution/{solutionId}/result.json`:

```jsonc
{
  "version": 1,
  "jobs": [            // 每个 Job = 一个数据组/subtask
    {
      "name": "subtask1",
      "score": 50,
      "scoreScale": 100,        // 占题面总分比例
      "status": "Accepted",
      "tests": [                // 该组内的测试点
        { "name": "1", "score": 25, "scoreScale": 50, "status": "Accepted", "summary": "" }
      ],
      "summary": "markdown 说明"
    }
  ],
  "summary": "整体 markdown 说明"
}
```

- 前端 `SolutionDetailsRenderer.vue` 渲染为 **jobs → tests 两级展开面板**(分数按 scoreScale 显示),兼容无 `version` 字段的旧格式;
- 前端通过 GET `problem/:pid/solution/:sid/details/download` 换取预签名 URL 后下载(`SolutionDetails.vue`);
- 可见性由题目/比赛设置控制:`solutionShowDetails` / `solutionShowOtherDetails` 等(`apps/server/src/schemas/problem.ts`)。

### 2.4 排行榜(ranklist JSON,存 OSS)

schema(`aoi/libs/common/src/schemas/ranklist.ts` `SRanklistSchema`),OSS key `contest/{contestId}/ranklist/{key}.json`:

```jsonc
{
  "version": 1,
  "topstar": {                 // 榜首折线图(可选)
    "list": [{ "userId": "...", "mutations": [{ "score": 100, "ts": 1690000000000 }] }]
  },
  "participant": {
    "columns": [               // 列定义
      { "name": "Total", "description": "总分" },
      { "name": "A", "description": "第一题", "problemId": "..." }
    ],
    "list": [
      {
        "rank": 1,
        "userId": "...",
        "tags": ["x"] ,         // 参赛者标签
        "columns": [{ "content": "100", "solutionId": "..." }]  // 单元格是 Markdown,可跳提交
      }
    ]
  },
  "metadata": { "generatedAt": 1690000000000, "description": "" }
}
```

- 前端 `RanklistRenderer.vue` 渲染表格(列头带 problemId 跳题目,单元格带 solutionId 跳提交记录,每页 50 条),`RanklistTopstars.vue` 用 echarts 画 topstar 分数时间线;
- 排行榜**内容完全由 runner 侧 ranker 决定**,AOI 只负责版本状态:`contests.ranklistState` 为 VALID(0)/ PENDING(1)/ INVALID(2),任何提交完成都会把比赛 ranklist 置 INVALID,等待 ranker 重新计算(`apps/server/src/routes/runner/solution.ts` complete 处理)。

### 2.5 OSS 对象键约定

| 对象 | 键 |
|---|---|
| 题目数据版本 | `problem/{problemId}/data/{hash}` |
| 提交的解答数据 | `solution/{solutionId}/data` |
| 评测详情 | `solution/{solutionId}/result.json` |
| 排行榜 | `contest/{contestId}/ranklist/{key}.json` |

(`apps/server/src/oss/key.ts`)

### 2.6 相关 MongoDB 集合

| 集合 | 关键字段 |
|---|---|
| `solutions` | state/taskId(唯一索引)/score/status/metrics/message/runnerId/problemDataHash/solutionDataHash |
| `runners` | orgId+key(唯一)/labels/name/version/message/ip/accessedAt |
| `contests` | ranklists(排行榜 key 列表)/ranklistState/ranklistUpdatedAt/ranklistRunnerId/ranklistTaskId |
| `contestParticipants` | results[problemId].lastSolution(最后一次提交引用,ranker 数据源) |
| `problemStatuses` | 普通题目(非比赛)的 lastSolutionScore/Status |

## 三、Runner 任务分发协议

### 3.1 注册(registrationToken → runnerId/runnerKey)

```
组织管理员(前端 Runner 管理页) → POST /api/org/:orgId/admin/runner/register
      → 签发 5 分钟有效的 JWT registrationToken(载荷 {orgId, runnerId})
azukiiro register --server <AOI地址> --token <registrationToken> --name ... --labels ...
      → POST /api/runner/register,提交 {name, labels[], version, registrationToken}
      → 服务端生成 runnerKey = randomBytes(32).base64,写入 runners 集合
      → 返回 {runnerId, runnerKey},azukiiro 自动写回本地配置文件
```

注册之后,一切请求带鉴权头 `X-AOI-Runner-Id` + `X-AOI-Runner-Key`(服务端 `onRequest` 钩子校验,`apps/server/src/routes/runner/index.ts`)。

**labels 决定 runner 能领到什么任务**:

| 任务类型 | 需要的 label |
|---|---|
| 普通评测(solution poll) | 任意(默认 `default`) |
| 排行榜(ranklist poll) | 必须含 `ranker` |
| 沙箱实例(instance poll) | 必须含 `instance:*` 前缀 |

### 3.2 评测任务(四个接口)

| 接口 | 说明 |
|---|---|
| `POST /api/runner/solution/poll` | 抢占一条 `state=PENDING` 且 label 匹配的 solution → QUEUED,绑定 taskId;返回完整 problemConfig、problemDataUrl/Hash、solutionDataUrl/Hash(OSS 未配置或数据缺失时返回 errMsg) |
| `PATCH /api/runner/solution/task/:solutionId/:taskId` | 上报 `{status, score, metrics, message}`(SolutionInfo),置 RUNNING |
| `GET .../task/:solutionId/:taskId/details/upload` | 换取评测详情 result.json 的预签名上传 URL |
| `POST .../task/:solutionId/:taskId/complete` | 置 COMPLETED;比赛内 → 更新 `contestParticipants.results[problemId].lastSolution` 并把 ranklistState 置 INVALID;普通题目 → 更新 `problemStatuses` |

### 3.3 实例任务(沙箱)

同构:`POST /api/runner/instance/poll` 按 `InstanceState`(ALLOCATING=3 / DESTROYING=1)下发创建/销毁任务,`PATCH/POST .../task/:instanceId/:taskId(/complete)` 上报进度与完成。

### 3.4 排榜任务

| 接口 | 说明 |
|---|---|
| `POST /api/runner/ranklist/poll` | 领取 `ranklistState=INVALID` 的比赛(需 label `ranker`),返回 {taskId, contestId, ranklists, ranklistUpdatedAt} |
| `GET .../task/:contestId/:taskId/contest\|problems\|participants\|solutions` | **增量同步**(since/lastId 游标分页),数据源 |
| `GET .../uploadUrls` | 每个 ranklist key 换取一个预签名上传 URL |
| `POST .../complete` | 提交 ranklistUpdatedAt,服务端比对一致 → VALID,不一致 → INVALID(防止覆盖新数据) |

### 3.5 状态流转全链路

```
用户 POST solution {hash,size}     → state=CREATED,上传解答 zip
用户 POST solution/:sid/submit    → state=PENDING
runner POST solution/poll         → state=QUEUED + runnerId/taskId
runner PATCH task/:sid/:taskId    → state=RUNNING(status="Running")
runner POST task/.../complete     → state=COMPLETED
   ├─ 比赛内: contestParticipants.results[pid].lastSolution ← 本次提交
   │          contests.ranklistState ← INVALID → ranker 重算
   └─ 普通题: problemStatuses.lastSolutionScore/Status ← 本次提交
```

## 四、Azukiiro 评测框架

Go 1.24 单二进制(module `github.com/fedstackjs/azukiiro`),自述 "Official runner for the AOI Project"。**评测机角色本身不需要 MongoDB**,只有 `ranker` 子命令需要(连接 AOI 同一个 Mongo)。

### 4.1 子命令一览

| 子命令 | 职责 | 关键参数 |
|---|---|---|
| `daemon` | 评测守护进程(连 AOI server 轮询评测) | `--concurrency`(默认 1,并行时 1 poller + N judger)、`--poll-interval`(默认 1s) |
| `judge` | 本地评测(不连服务器,调试用) | `--problem-config --problem-data --solution-data [--env JSON]` |
| `ranker` | 排行榜守护进程(需 `dbAddr` 连 Mongo) | — |
| `instancer` | 沙箱实例守护进程 | — |
| `register` | 向 AOI 注册 runner | `--server --token --name --labels --force` |
| `info` | 打印版本/适配器/配置路径/storagePath/serverAddr/runnerId | — |

### 4.2 评测管线(`judge/`)

串行模式(`judge.Poll`,默认):

```
client.PollSolution          → 认领任务(服务器置 QUEUED)
PATCH {score:0, status:"Running", message:"Preparing solution"}
storage.PrepareFile ×2       → 下载题目数据与解答数据(sha256 校验,缓存 cache/<hash>,3 次重试)
PATCH {status:"Running", message:"Judging"}
adapter := GetAdapter(problemConfig.judge.adapter)
adapter.Judge(ctx, task)     → 适配器产出 SolutionInfo + SolutionDetails
    (评测中途 Update() 经 PATCH 上报进度,UploadDetails() 经预签名 URL 上传 result.json)
SaveSolutionDetails → PatchSolutionTask → CompleteSolutionTask
出错: 若错误实现 JudgeError 接口则上报其 Details,否则默认 {score:0, status:"Error"} + 错误摘要
```

并行模式:`ParallelPoller` 把数据下载/适配器检查提前做掉(状态 `Queued/Preparing solution` → `Queued/Waiting for judge`),任务入 channel 队列,`ParallelJudger` worker 并发评测。

### 4.3 适配器体系(插件式,包 init() 注册)

**judge 适配器**(按 `problemConfig.judge.adapter` 名路由):

| 适配器 | 用途 | 运行时依赖 |
|---|---|---|
| `uoj` | 复用 UOJ 社区版 judger 二进制,传统 OI 评测 | Linux + `bwrap` 沙箱 + `/opt/uoj_judger/main_judger`(Windows 下为空实现) |
| `deno` | 题目携带 .ts 评测脚本(Deno 执行) | `deno` 可执行文件 |
| `glue` | 万能适配器:任意 shell/bash 命令评测(需 `unsafe` 编译标签构建) | shell |
| `dummy` | 恒 AC(100 分),联调用 | 无 |
| `flag` | 比对解答 zip 里 `answer.json` 的 `flag` 字段与题目配置 | 无 |
| `vjudge` | 同步 vjudge.net 的评测结果 | 外网可达 vjudge.net |

**uoj 适配器详解**(OI 评测的关键路径):
- 评测配置来自题目数据 zip 内的 **`problem.conf` 文本文件**(格式见下方模板),其中 `subtask_score_N` 定义各数据组分值;
- 解答 zip 内必须含 **`.metadata.json`**,写明 `language`(白名单:C++/C++11/C++14/Python2/Python3,默认 C++14),写入 `submission.conf`;
- `bwrap` 只读绑定题目目录、写绑定 work/result 目录执行 `/opt/uoj_judger/main_judger`;judger 产出 **UOJ 风格 XML**(`result.txt`):`Result{Score,Time,Memory,Error,Details}`,Details 含 `Tests[]` 与 `Subtasks[]`;
- azukiiro 把 XML 解析成 `SolutionInfo` + `SolutionDetails`:每个 subtask 归一化成一个 Job(`subtask_score_N` 做 scale),无 subtask 时生成 `"Default"` Job;最终 status 取首个非 Accepted 的 Job。

**problem.conf 模板**(uoj 适配器,题目数据 zip 根目录):

```conf
# ============ UOJ 传统题 problem.conf 模板 ============
# 说明: 本文件由 UOJ judger 二进制读取(题目数据需与 UOJ-System 数据格式一致),
#        azukiiro 只额外读取 subtask_score_N 用于生成评测详情 Job(必读,见下)。
#        每行只能有一条配置,格式为 "key value",key 与 value 之间用单个空格!
#        键值间不要用 Tab 或多个空格(azukiiro 按第一个空格切分)。

# 使用内置评测器: 传统题必须 on;off 表示自定义 judger(通信题等)
use_builtin_judger on

# 内置 checker(输出比对器):
#   ncmp  整数比对(long long 范围内)
#   wcmp  文本比对
#   rcmp  实数比对(相对误差 1.5e-6)/ rcmp4 / rcmp6 / rcmp7 / rcmp9(不同精度)
#   yesno 单行 YES/NO 比对(忽略大小写)
# 不写这一行 = 使用 SPJ: 需提供基于 testlib.h 的 chk.cpp 放在题目数据根目录
use_builtin_checker ncmp

# 测试点个数(不使用 subtask_in_folder 时必须设置)
n_tests 20

# 数据文件命名: <input_pre><编号>.<input_suf>,如 a1.in / a2.out
input_pre a
input_suf in
output_pre a
output_suf out

# 时间 / 内存 / 输出限制
time_limit 1          # 秒(整数),默认 1;也可用 time_limit_ms 1500 精确到毫秒
memory_limit 256      # MB,默认 256
output_limit 64       # MB,默认 64

# ---- 可选配置(按需取消注释,遵循 UOJ-System 规范)----
# n_ex_tests 0          # 额外(不计分)测试点个数
# ex_input_pre ex_a
# ex_input_suf in
# ex_output_pre ex_a
# ex_output_suf out
# n_sample_tests 0      # 样例测试点个数(展示用,不计分)
# submit_answer off     # 提交答案题置 on
# subtask_in_folder on  # 测试点按文件夹组织时置 on

# ---- 子任务(数据组)配置 ----
# 不配子任务: azukiiro 把全部测试点合并为一个 "Default" Job,总分取 judger 结果
# 配子任务时:
#   subtask_end_N    第 N 个子任务结束于哪个测试点(如 end_1 10 = 测试点 1~10)
#   subtask_score_N  第 N 个子任务的分值
#                    注意: 这是 azukiiro 的必读字段——每个 Job 的 ScoreScale 取自它,
#                    某个子任务缺了该行,该子任务会直接报 Judge Error!
subtask_end_1 10
subtask_score_1 30
subtask_end_2 20
subtask_score_2 70
```

**子任务分数换算**:uoj 适配器将 UOJ judger 产出的原始 subtask 分数按 `subtask_score_N` 归一化为百分制(`Score = 原始分 / subtask_score_N × 100`),例如子任务 1 原始分 30(满分 30)→ 前端显示 100;原始分 15 → 显示 50。

**deno / glue 的上报协议(FIFO + key=value 行)**:
- 环境变量:`AZUKIIRO_PROBLEM_DATA_DIR`、`AZUKIIRO_SOLUTION_DATA_DIR`、`AZUKIIRO_REPORT`(FIFO 路径)、`AZUKIIRO_DETAILS`(details.json 路径);
- 向 FIFO 写 `score=100`、`status=Accepted`、`message=...`、`metrics={"cpu":..}`、`commit=1`(触发上报);`details.json` 可直接写完整 SolutionDetails。

**instancer 适配器(docker)**:
- 题目数据 zip 内放 `compose/compose.yml`,`StartInstance` 复制到 `instances/<instanceId>/` 并转换:要求存在外部 `caddy` 网络、入口服务打 `caddy` 标签生成访问域名(`<instanceId>.inst.localhost`,默认 domainSuffix),`docker compose up -d --no-build --pull never` 启动;
- `DestroyInstance`:`docker compose down -v` + 删除实例目录;
- 配置:`instancer.docker.startTimeout`(默认 30s)/ `domainSuffix`(默认 `.inst.localhost`)/ `networkName`(默认 `caddy`)/ `hostInstancesPath`。

### 4.4 排榜器(`ranker/ranker.go`)

非 ICPC 罚时模式,**取每道题最后一次提交**:

```
1. PollRanklist 领取 INVALID 比赛任务
2. GetRanklistParticipants 增量同步(upsert 到 Mongo 集合 contest-<contestId>-participants,主键 _id)
3. TotalScore = Σ result.LastSolution.Score;LastSolutionTime = max(completedAt)
4. 排序:ByTotalScoreAndTime —— 分数降序,同分按最后提交时间升序(先 AC 者在前)
5. 生成 Ranklist:列 = Total + 每题 slug;行 = {rank, userId, tags, columns[content]}
   每个 ranklists(DTO key)各生成一份,经预签名 URL 上传 OSS
6. CompleteRanklistTask{ranklistUpdatedAt} → 服务端比对 → VALID
```

### 4.5 存储与缓存(`storage/`)

- `storagePath`(默认 `/var/lib/azukiiro`):`cache/<sha256>` 内容寻址缓存(天然去重,3 次重试下载)、`tmp/` 解压目录、`instances/`;
- 解压调用系统 `unzip`,并删除 zip 内的符号链接防安全风险。

### 4.6 配置与部署

**配置文件**(viper):搜索路径 `/etc/azukiiro/` → `$HOME/.config/azukiiro/` → `$HOME/.azukiiro/` → 当前目录,文件名 `config`(yaml/json/toml 皆可),`-c` 可指定单文件;**config 文件必须预先存在**(ReadInConfig 失败直接退出);`register` 会把 runnerId/runnerKey 写回该文件。

| 键 | 默认 | 必填场景 |
|---|---|---|
| `serverAddr` | 无 | 全部(daemon/ranker/instancer/register) |
| `runnerId` / `runnerKey` | 无 | daemon/ranker/instancer(register 后自动写入) |
| `storagePath` | `/var/lib/azukiiro` | — |
| `dbAddr` | 无 | 仅 ranker(MongoDB URI,一般复用 AOI 的 Mongo) |
| `instancer.docker.*` | 见 4.3 | 仅 instancer |

**发布产物**:GitHub Releases 按 `assets/friendly-filenames.json` 友好名发布 zip,如 Linux x86_64 为 `azukiiro-linux-64.zip`(内含 `build/azukiiro` 二进制),附 `.dgst` 校验文件(md5/sha1/sha256/sha512)。仓库自带 systemd 模板 `assets/systemd/azukiiro@.service`(`ExecStart=/opt/azukiiro/build/azukiiro %i`,以 `azukiiro@daemon` 之类实例名启动各子命令)。**仓库没有 Dockerfile,azukiiro 以裸二进制运行**。

## 五、Azukiiro ↔ AOI 适配关系对照

| AOI 侧(前端可感知) | Azukiiro 侧 | 对应关系 |
|---|---|---|
| `problem-config.json` 的 `judge.adapter` | `judge.RegisterAdapter` 注册表(4.3) | adapter 名字符串直配,不认识的 adapter 报 Internal Error |
| `judge.config` 自由对象 | 各适配器的 `XxxAdapterConfig`(JSON 解析) | uoj: SandboxMode;deno: Script/Timeout;flag: Flag;vjudge: Oj/ProbNum;glue: Command/Run/Timeout |
| Solution 的 `state` 整数 | 不直接操作,由 poll/PATCH/complete 驱动 | 服务端单方面推进状态机 |
| Solution 的 `status` 字符串 | `SolutionInfo.Status` | 适配器直接产出(PATCH 上报),前端做展示映射 |
| `score` / `metrics` | `SolutionInfo.Score / Metrics` | PATCH 时上报,cpu/mem 键前端有 i18n 文案 |
| 评测详情 `result.json`(jobs/tests) | `SolutionDetails`(Jobs/Tests/Summary) | azukiiro 生成 → 预签名 URL 上传 → 前端渲染 |
| 排行榜 `ranklist.json` | `ranker` 生成(按 ranklists key) | ranker 守护进程专属任务,label 必须含 `ranker` |
| `runners` 集合 / 前端 Runner 管理页 | `register` 子命令 | 注册后即出现在前端组织管理页 |
| 沙箱实例 `instances` 状态机 | `instancer` + docker 适配器 | label 需 `instance:*`,compose 定义在题目 zip 内 |

**典型题目配置示例**(OI 题,uoj 适配器):

```jsonc
// problem.json(题目数据 zip 内)
{
  "label": "A+B Problem",
  "solution": { "maxSize": 10485760 },
  "judge": {
    "adapter": "uoj",
    "config": { "sandboxMode": "bwrap" }
  }
}
```

```text
# 题目数据 zip 的目录结构(uoj 适配器)
problem.zip
├── problem.json      # 上述配置(adapter: "uoj")
├── problem.conf      # UOJ 评测配置,完整模板见 4.3 节
├── chk.cpp           # 仅 SPJ 题需要(testlib.h 编写,此时 problem.conf 不写 use_builtin_checker)
├── a1.in  a1.out     # 测试点(n_tests 个,命名按 input_pre/output_pre 与编号)
└── a2.in  a2.out     # ...
```

**提交语言约定**:uoj 适配器从解答 zip 的 `.metadata.json` 读 `language`(白名单 C++/C++11/C++14/Python2/Python3,默认 C++14);前端提交表单按 `submit.form` 配置生成(`language` 下拉由 `submit.form.items` 或文件 `type.editor` 控制),前后端通过同一个 zip 的 metadata 衔接。

## 七、部署联动(setup_azukiiro.sh)

评测机需要安装 `unzip`(解压数据);按所用适配器追加依赖:

| 适配器 | 依赖 | 安装方式 |
|---|---|---|
| 通用 | unzip、coreutils(find) | 发行版包管理器 |
| uoj | `bwrap`(bubblewrap)+ `/opt/uoj_judger/main_judger` | 包管理器 + UOJ 仓库构建 |
| deno | `deno` 可执行文件 | deno 官方安装脚本 |
| glue | shell(需 `unsafe` 编译标签构建的二进制) | — |
| instancer | docker CLI + 外部 `caddy` 网络 + 预下载镜像 | Docker 官方脚本 |
| ranker | MongoDB(复用 AOI 的 Mongo) | AOI 部署自带 |

与 `setup_aoi.sh` 的拓扑关系:azukiiro 可以部署在**任意 Linux 机器**(与 AOI server 同机亦可),只要网络可达 AOI 的 API(反代 80/443 或直连 1926),并持有 Mongo 连接串(仅 ranker 需要)。注册流程需要 AOI 组织管理员在 Runner 管理页生成 registrationToken(5 分钟有效),由 `register` 子命令完成绑定。systemd 模板:`azukiiro@daemon.service`(评测)、`azukiiro@ranker.service`(排榜,可选)、`azukiiro@instancer.service`(沙箱,可选)。
